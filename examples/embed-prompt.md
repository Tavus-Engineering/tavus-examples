How the element works

- Install: `npm install @tavus/embed`, then `import "@tavus/embed"` once at the app entry, as a static import, even when the element itself is mounted later from a button. Do not load the package with a lazy `import()`: in Vite's dev server that triggers a dependency re-optimisation mid-session, which can leave the page with two copies of React and a blank screen. The import registers the element and ships React JSX typings, so `<tavus-embed>` type-checks. In a server-rendered framework (Next.js, Remix, Nuxt, SvelteKit) the element is browser-only: do the import inside a client component (`"use client"` in Next.js) or after mount. Without a bundler, and on site builders such as Webflow, Framer, Wix or Squarespace, use the script tag in the page's custom code: `<script src="https://unpkg.com/@tavus/embed@latest"></script>` plus the element in an HTML embed block.
- Sizing is your job. The element fills its parent and adapts to whatever box it gets, so give the wrapper a definite size. Orientation and ratio depend on the use case and are the user's call: a section or a card on a desktop page is usually landscape (16:9 is the recommended default, 4:3 or wider also work), a kiosk, a phone layout or a tall sidebar is portrait (9:16 recommended). Below 56.25rem (900px) of container width the element switches to its compact portrait layout on its own; when the parent has no definite height it falls back to 16:9 above that width and 9:16 below. On phones give a landscape wrapper a 9:16 box with a media query, as the examples do; a short 16:9 strip there wastes the screen. Its type scale follows the root font size, so a larger root font gives larger controls and text (useful on a big kiosk screen). Ask when the answer to question 1 does not make the shape obvious.
- Attributes configure the agent for this page: who the visitor is and what the page is about (context), the first thing the agent says, memory across visits, whether the camera starts on, how the preview is laid out (`layout`), whether the card expands into a modal for the call (`expand-options`), and page-specific overrides of the portal settings such as the preview copy or skipping the device check (`override-config`, a JSON string merged over the deployment's `customization`). The current attribute list, their shapes and defaults are in the embed reference below; read it rather than guessing names. Set context and a greeting only when the page knows something worth telling the agent, such as a name, a chosen topic or the product; a plain section needs neither.
- The page talks to the element through methods and listens through events. Methods exist only after the element reports ready. Events are DOM `CustomEvent`s named `tavus:*` that bubble from the element to `document`, with the payload in `event.detail`. When the page needs methods or events, use the `TavusIntegration` helper exported by the package, created after the element is in the DOM; it wraps the methods and gives typed `on`/`off` subscriptions. A page that only shows the element needs none of this.
- Magic Canvas: the agent can show interactive cards (questions, calendars, charts) inside the element on its own. Nothing to build on the page.

How to do the common things properly

These are the contracts the element keeps. Exact payloads and signatures are in the reference below; the order of operations and what fires when are here, because that is what tends to get invented.

- Knowing the element is ready. `tavus:ready` fires once per element instance after the deployment configuration has loaded, and it is the moment the methods are installed. Subscribe before or right after mounting, in the same tick, so you do not miss it. A recreated element fires it again. Nothing below works before it.
- Starting a conversation. By default the element shows its own Start button on its preview screen, with the deployment's copy, and the visitor starts there; nothing to wire. When your flow needs its own trigger (a button elsewhere on the page, a form submit, a route change, a kiosk reset loop), start programmatically with `startConversation()`; it takes the same path as the built-in button: device permission prompt, bot check if the deployment has one, then the join. Two valid shapes for a programmatic start: if the element is already on the page (hidden is fine), call `startConversation()` from the click once ready has fired; if the click is what mounts the element, call it inside the ready handler. Calling it twice, from a double tap or two handlers, still starts one conversation; a call while one is live does nothing. It never throws and never rejects. Failures arrive as `tavus:error` `{ code, message }`; the daily limit, a busy agent and a bot check that cannot run move the element to its own unavailable screen and fire `tavus:mode-change` with `unavailable` instead. Do not call `startConversation()` again from a `tavus:error` or `tavus:conversation-ended` handler: the element already shows the visitor a Try again button where a retry can help, and the other failures repeat. A start lands on the element's device check when the deployment has it on; when the visitor has already pressed your button, skip it with `override-config` `{"customization":{"show_haircheck":false}}` so the call opens without a second click. Success is `tavus:conversation-started` `{ conversationId }`, which is also when the agent can hear and be messaged.
- Preparing a conversation ahead of time. `createConversation()` creates the room without joining it, so a later `startConversation()` joins in well under a second instead of waiting for the agent to spin up. Use it when a call is clearly coming (a form the visitor is filling, a page they are about to leave for the call page), never on every page view. Set `conversational-context` and `custom-greeting` before calling it; they are read at creation, so if they change afterwards create again (the element ends the room nobody joined). It fires `tavus:conversation-created` `{ conversationId }` and resolves with the same; it rejects when the room could not be created, in which case do nothing, the later start creates one as usual. Every creation is a real conversation on the backend even if nobody joins, so end it with `endConversation()` when the visitor leaves without starting; the element also ends it when the page is left. If a start arrives while the create is still in flight, the start joins that attempt and the created event does not fire, so do not gate the UI on it.
- Ending a conversation. `endConversation()` leaves a live call, cancels a start or device check still pending, and ends a prepared room nobody joined. `tavus:conversation-ended` `{ conversationId }` follows for a call that was live, and the element shows its after-call screen with its own restart button. Unmounting the element also ends its call, but without an ended event, so if you mount per page or per modal, treat your own unmount as the end. For a fresh preview for the next visitor, recreate the element (in React, change its key) rather than reusing the one on the after-call screen.
- Sending something into the conversation. Only after `tavus:conversation-started`; before that there is nobody to receive it. `sendMessage({ event_type: "conversation.respond", properties: { text } })` makes the agent answer the text as if the visitor had said it (suggested-question chips, a page event the agent should react to). `conversation.echo` makes the agent say the text verbatim. `conversation.interrupt` stops it mid-sentence. `conversation.append_llm_context` and `conversation.overwrite_llm_context` change what the agent knows mid-call (the visitor changed a selection, a new page loaded). The helper also accepts a plain string and wraps it as `conversation.respond`. `el.tavus.sendChat(text)` on the element sends a chat message as the visitor instead. There is no way to make the agent speak audio you supply.
- Reading what is said. Utterances arrive on `tavus:protocol-message` with `detail.event_type === "conversation.utterance"`, `detail.properties.role` of `"user"` or `"replica"` (the agent), and `detail.properties.speech`. Complete utterances carry no `final` field; streaming partials of the same sentence carry `final: false` and grow word by word. Keep only the complete ones, or a transcript shows every partial as its own line. `tavus:chat-message` and `tavus:message` exist in the type definitions for compatibility and never fire; do not build on them.
- Letting the agent act on the page. Everything the agent does on the page goes through tools: a tool is defined on the PAL (in the PAL Maker or through the API) with `delivery: { app_message: true }`, and when the agent decides to use it the page gets `tavus:tool-call` `{ name, arguments, tool_call_id? }` with `arguments` as a JSON string matching the tool's schema. The page does the work (updates the cart, opens the product, fills the form), then replies with `sendMessage({ event_type: "conversation.tool_result", properties: { tool_call_id, output, status: "success" } })` using the same `tool_call_id`; the agent then speaks from the result. Without an id there is nothing to pair a reply with, so just act. Send `status: "error"` to have the agent acknowledge a failure. No tool on the PAL means no event on the page, however the page is wired; so when actions are wanted and no tools exist yet, produce the tool specification for the PAL alongside the handlers. The agent only knows what the page tells it: pass the current state (cart, open product, the visitor's selection) in `conversational-context` at the start and with `append_llm_context` when it changes mid-call.
- Changing settings while the element is mounted. `updateConfig(patch)` takes the same shape as `override-config` and deep-merges it over what is in effect, for example a theme switch. `expand-options` is observed too: changing the attribute updates the card, and disabling it during a call collapses the modal.
- Knowing where the element is. `tavus:state-change` `{ state }` tracks the connection (idle, initializing, connecting, connected, disconnecting, ended, error). `tavus:mode-change` `{ mode }` tracks the screen (idle for the preview, haircheck, call, ended for the after-call screen, unavailable). With `expand-options`, the modal is open while the mode is haircheck or call. The modal is a `<dialog>` inside the element's shadow root on the browser's top layer; the element itself stays where it is in the page, so the page owns no modal code and needs no scroll lock.

Not possible, not needed, or not yours to do

- No backend, no API key, no calls to the Tavus API from the page. The browser talks to Tavus with the deployment id alone. Bot protection, allowed origins, daily limits, the device check, the theme and the agent's persona are portal settings; do not try to set them from code or invent attributes for them.
- Do not style anything inside `<tavus-embed>`; it renders in its own shadow DOM. Colours, radius, fonts and copy come from the portal or from `override-config`.
- Do not poll for state or wait on timers for readiness; every transition has an event above.
- Do not add a camera or microphone preview, a mute button, captions or a leave button of your own; the element has them. On mouse devices the call controls hide until the pointer moves; on touch screens they stay visible.
- Attributes, methods and events are exactly those in the reference. If a name is not there or in the installed `.d.ts`, it does not exist.
- Keep the page copy about the product. The wiring stays in code.
