How the element works

- Install: `npm install @tavus/widget`, then `import "@tavus/widget"` once at the app entry, as a static import. Do not load the package with a lazy `import()`: in Vite's dev server that triggers a dependency re-optimisation mid-session, which can leave the page with two copies of React and a blank screen. The import registers the element and ships React JSX typings, so `<tavus-widget>` type-checks. In a server-rendered framework (Next.js, Remix, Nuxt, SvelteKit) the element is browser-only: do the import inside a client component (`"use client"` in Next.js) or after mount. Without a bundler, and on site builders such as Webflow, Framer, Wix or Squarespace, paste both lines into the site's custom code before `</body>`: `<tavus-widget deployment-id="…"></tavus-widget>` and `<script src="https://unpkg.com/@tavus/widget@latest"></script>`.
- Placement is not your job. The widget positions itself relative to the viewport, so put the element anywhere in the document, typically once in the root layout just before `</body>`. Its variant (tiny, compact, full), corner, expand behaviour and avatar are deployment settings in the portal, not attributes; do not wrap it, size it or position it, and do not render more than one on a page.
- Attributes configure the agent for this page: who the visitor is and what the page is about (context), the first thing the agent says, memory across visits, whether the camera starts on, and page-specific overrides of the portal settings (`override-config`, a JSON string merged over the deployment's `customization`, for example to skip the device check or change the launcher text under `customization.widget.text`). The current attribute list, their shapes and defaults are in the widget reference below; read it rather than guessing names. Set context and a greeting only when the page knows something worth telling the agent, such as a name, the product on the page or the visitor's plan; a plain site needs neither. There is no `layout` and no `expand-options` on the widget; those belong to the embed.
- The page talks to the element through methods and listens through events. Methods exist only after the element reports ready. Events are DOM `CustomEvent`s named `tavus:*` that bubble from the element to `document`, with the payload in `event.detail`. When the page needs methods or events, use the `TavusIntegration` helper exported by the package (`new TavusIntegration()` defaults to `tavus-widget`), created after the element is in the DOM; it wraps the methods and gives typed `on`/`off` subscriptions. A page that only shows the launcher needs none of this.
- Magic Canvas: the agent can show interactive cards (questions, calendars, charts) inside the popup on its own. Nothing to build on the page.

How to do the common things properly

These are the contracts the element keeps. Exact payloads and signatures are in the reference below; the order of operations and what fires when are here, because that is what tends to get invented.

- Knowing the element is ready. `tavus:ready` fires once per element instance after the deployment configuration has loaded, and it is the moment the methods are installed. Subscribe before or right after mounting, in the same tick, so you do not miss it; if the element may already be ready when your code runs, check whether `startConversation` is installed before waiting. A recreated element fires it again. Nothing below works before it.
- Opening and closing the popup. The visitor opens it by tapping the launcher; `open()` and `close()` do the same from the page. Opening shows the preview with the deployment's copy and Start button. `close()` is the popup's own close path: it ends a call in progress and cancels a pending start before it collapses, so a close is an end and nothing keeps running behind the launcher. Use `open()` for a trigger that should let the visitor press Start themselves, and `startConversation()` for one that should go straight into the call.
- Starting a conversation. By default the visitor taps the launcher and then the Start button in the popup; nothing to wire. When your own trigger should start the call directly (a "Talk to us" button, a form submit), call `startConversation()`: it opens the popup and takes the same path as the built-in button, device permission prompt, bot check if the deployment has one, then the join, so a host button can be the only thing the visitor touches. Call it from the click once ready has fired. Calling it twice, from a double tap or two handlers, still starts one conversation; a call while one is live does nothing. It never throws and never rejects. Failures arrive as `tavus:error` `{ code, message }`. The daily limit, a busy agent and a bot check that cannot run also move the popup to its own unavailable screen and fire `tavus:mode-change` with `unavailable`, usually right after the error event, so treat the mode change as the signal and the error as something to log. Do not call `startConversation()` again from a `tavus:error` or `tavus:conversation-ended` handler: the element already shows the visitor a Try again button where a retry can help, and the other failures repeat. A start lands on the element's device check when the deployment has it on; when the visitor has already pressed your button, skip it with `override-config` `{"customization":{"show_haircheck":false}}` so the call opens without a second click. Success is `tavus:conversation-started` `{ conversationId }`, which is also when the agent can hear and be messaged.
- Preparing a conversation ahead of time. `createConversation()` creates the room without joining it, so a later `startConversation()` joins in well under a second instead of waiting for the agent to spin up. Use it when a call is clearly coming (a form the visitor is filling, a pricing page where the launcher is the next step), never on every page view, and never on every page of a site. Set `conversational-context` and `custom-greeting` before calling it; they are read at creation, so if they change afterwards create again (the element ends the room nobody joined). It fires `tavus:conversation-created` `{ conversationId }` and resolves with the same; it rejects when the room could not be created, in which case do nothing, the later start creates one as usual. Every creation is a real conversation on the backend even if nobody joins, so end it with `endConversation()` when the visitor leaves without starting; the element also ends it when the page is left. If a start arrives while the create is still in flight, the start joins that attempt and the created event does not fire, so do not gate the UI on it.
- Ending a conversation. `endConversation()` leaves a live call, cancels a start or device check still pending, and ends a prepared room nobody joined. `close()` during a call does the same. `tavus:conversation-ended` `{ conversationId }` follows for a call that was live, and the popup shows its after-call screen with its own restart button. Unmounting the element also ends its call, but without an ended event; in a single-page app keep the element in a layout that survives navigation rather than mounting it per route, or a route change will end the visitor's call.
- Keeping the agent informed as the visitor moves around. In a single-page app with a persistent layout the element lives in that layout and the conversation survives client-side navigation; a full page load unmounts it and ends the call. Set `conversational-context` from the page before the call starts; once the call is live, attributes are not re-read, so send `conversation.append_llm_context` with what changed (the visitor opened a product, moved to pricing, changed a selection) instead.
- Sending something into the conversation. Only after `tavus:conversation-started`; before that there is nobody to receive it. `sendMessage({ event_type: "conversation.respond", properties: { text } })` makes the agent answer the text as if the visitor had said it (suggested-question chips, a page event the agent should react to). `conversation.echo` makes the agent say the text verbatim. `conversation.interrupt` stops it mid-sentence. `conversation.append_llm_context` and `conversation.overwrite_llm_context` change what the agent knows mid-call. The helper also accepts a plain string and wraps it as `conversation.respond`. `el.tavus.sendChat(text)` on the element sends a chat message as the visitor instead. There is no way to make the agent speak audio you supply.
- Reading what is said. Utterances arrive on `tavus:protocol-message` with `detail.event_type === "conversation.utterance"`, `detail.properties.role` of `"user"` or `"replica"` (the agent), and `detail.properties.speech`. Complete utterances carry no `final` field; streaming partials of the same sentence carry a boolean `final` field (`false` while the sentence grows) and may carry `is_interrupted`. Keep only the ones without a `final` field, or a transcript shows every partial as its own line. `tavus:chat-message` and `tavus:message` exist in the type definitions and never fire; do not build on them.
- Letting the agent act on the page. Everything the agent does on the page goes through tools: a tool is defined on the PAL (in the PAL Maker or through the API) with `delivery: { app_message: true }`, and when the agent decides to use it the page gets `tavus:tool-call` `{ name, arguments, tool_call_id?, seq?, turn_idx? }` with `arguments` as a JSON string the model wrote for the tool's schema. The element does not validate it: parse it in a try/catch, check the fields you use and the values you act on (an id that exists, a route you allow), and reply with `status: "error"` when they do not hold. The page does the work (opens the product, fills the form, navigates), then replies with `sendMessage({ event_type: "conversation.tool_result", properties: { tool_call_id, output, status: "success" } })` using the same `tool_call_id`; the agent then speaks from the result. Without an id there is nothing to pair a reply with, so just act. Send `status: "error"` to have the agent acknowledge a failure. No tool on the PAL means no event on the page, however the page is wired; so when actions are wanted and no tools exist yet, produce the tool specification for the PAL alongside the handlers. Navigation is a common tool on a widget ("take me to pricing", "show me the plans"): scrolling to a section or a client-side route change keeps the call going, while a full page load unmounts the element and ends it, so implement navigation tools with anchors or the app's router and keep the element in the layout that survives the change.
- Changing settings while the element is mounted. `updateConfig(patch)` takes the same shape as `override-config` and deep-merges it over what is in effect, for example a theme switch or new launcher text.
- Knowing where the element is. `tavus:state-change` `{ state }` tracks the connection (idle, initializing, connecting, connected, disconnecting, ended, error). `tavus:mode-change` `{ mode }` tracks the screen (idle for the preview, haircheck, call, ended for the after-call screen, unavailable).

Not possible, not needed, or not yours to do

- No backend, no API key, no calls to the Tavus API from the page. The browser talks to Tavus with the deployment id alone. Bot protection, allowed origins, daily limits, the device check, the theme, the launcher's look and the agent's persona are portal settings; do not try to set them from code or invent attributes for them.
- Do not style anything inside `<tavus-widget>`; it renders in its own shadow DOM. Colours, radius, launcher text and copy come from the portal or from `override-config`; the font is fixed.
- Do not build your own launcher, popup, camera preview, mute button, captions or leave button; the element has them. If the design needs a launcher of its own, hide nothing and add nothing: use a page button that calls `open()` or `startConversation()` and leave the element's launcher as it is, or ask whether the embed is the better fit.
- Do not poll for state or wait on timers for readiness; every transition has an event above.
- Attributes, methods and events are exactly those in the reference. If a name is not there or in the installed `.d.ts`, it does not exist.
- Keep the page copy about the product. The wiring stays in code.
